# בדיקות אוטומטיות ב־GitHub

ההגדרה נמצאת ב־`.github/workflows/ci.yml`. GitHub Actions מריץ אותה בכל push לכל ענף, בכל פתיחה או עדכון של Pull Request, ב־merge queue, וגם ידנית דרך Actions → CI → Run workflow.

קומיט מקומי אינו מפעיל את GitHub: ההרצה מתחילה כשדוחפים אותו. Push עם כמה קומיטים בודק את המצב הסופי שנדחף. הרצה חדשה באותו ענף ואותו סוג אירוע מבטלת הרצה קודמת כדי לחסוך דקות. Push לענף עם PR פתוח יוצר שתי הרצות, כי כל אירוע נבדק בנפרד.

## מה נבדק

| Check | מטרה |
| --- | --- |
| Unit tests | לוגיקה, חישובים, חוזי נתונים, תכנון, שיחה, שמירה, הרשאות וטיפול בשגיאות. `npm test`. חמש בדיקות שדורשות Firebase מדולגות כאן ונבדקות ב־Firebase integration. |
| Types, production build and browser tests | בניית Next.js, בדיקת TypeScript ובדיקות Playwright בדפדפן Chromium מול שרת production מקומי. מכסה תהליכים, עריכות, שחזור אחרי רענון, RTL ותצוגות מובייל לפי הבדיקות הקיימות. |
| Firebase integration | Auth ו־Firestore אמיתיים באמולטורים, בפרויקט `demo-shadowui-catalog`: בעלות, הרשאות, גרסאות, התנגשויות כתיבה וסנכרון חשבונות. `npm run test:catalog`. |

הסביבה מותקנת מאפס באמצעות `npm ci` ו־package-lock.json. שלוש העבודות רצות במקביל; בדיקות הדפדפן רצות עם worker אחד כדי למנוע התנגשויות במצב משותף. כשל אמיתי אינו מוסתר בניסיון חוזר אוטומטי. `test.only` בבדיקות Playwright מכשיל CI כדי שלא יהיה אפשר להעלות בטעות הרצה שבודקת רק בדיקה אחת.

## בדיקות שפה ואנימציה

בדיקות שמשנות את שפת הממשק מאתרות את שדה המטרה וכפתור היצירה לפי התפקיד והשם הנגיש בעברית או באנגלית. בדיקות מעבר בין תצוגות מתחילות לדגום את גובה הכרטיס באירוע הלחיצה עצמו, לפני עדכון ה־React; כך עומס CI או הקלטת וידאו אינם גורמים להחמצת האנימציה בזמן ההמתנה לסיום פעולת Playwright. עדיין נדרש שינוי גובה משמעותי, גבהי ביניים בפועל והתייצבות בסיום — אין ניסיונות חוזרים או הקלה בתנאים.

## איך קוראים תוצאה

ב־PR פותחים Checks, או בריפו פותחים Actions → CI → ההרצה. ירוק מציין שהבדיקות עברו; אדום מציין כשל; צהוב מציין המתנה או עבודה. פותחים את ה־job ואת ה־step שנכשל ורואים את השגיאה. כשל יכול לנבוע מהקוד או מתשתית ההרצה, ולכן קוראים את הלוג.

בדיקות הדפדפן שומרות HTML report ובכישלון גם צילום מסך ו־trace. מורידים את `browser-results` מתוך Artifacts. לפתיחת trace: `npx playwright show-trace path/to/trace.zip`. לוגי Firebase נשמרים בכישלון. התוצרים נשמרים שבעה ימים.

## מגבלות מכוונות

אין שימוש במפתחות production או בקריאות AI בתשלום. תגובות AI מדומות בבדיקות הממשק; בדיקות אלה אינן הוכחה לאיכות או לזמינות מודל אמיתי. בדיקת `catalog-live-db` ובדיקת כניסת מנהל דרך popup דורשות opt-in וסביבה נפרדת ולכן מדולגות בהרצת הדפדפן הרגילה. הרשאות מנהל נבדקות גם באינטגרציית Firebase. ה־CI אינו בדיקת האתר שכבר נפרס ואינו מבצע deployment.

## למנוע מיזוג כשהבדיקות נכשלות

הרצת Checks כשלעצמה אינה חוסמת Merge. לאחר שהקובץ נדחף והבדיקות מופיעות בגיטהאב, מגדירים Settings → Rules → Rulesets עבור הענף הראשי, מפעילים Require status checks to pass ומוסיפים את שלושת שמות ה־Checks מהטבלה. בריפו הזה כבר פעיל Ruleset בשם `Required CI checks for main`: שלוש הבדיקות נדרשות על `main`, נדרש ענף מעודכן, ואין חריגות עקיפה. לכן שינויים חדשים מעבירים דרך ענף ו־PR, ממתינים ל־Checks ירוקים ורק אז ממזגים. Push לענף אחר עדיין מפעיל בדיקות לפי ההגדרה לעיל.

## הרצה במחשב

```sh
npm ci
npm test
npm run build
npm run typecheck
```

לבדיקות דפדפן בתצורת CI (שרת עצמאי בפורט 3000):

```sh
npx playwright install chromium
CI=true npm run test:e2e
```

לבדיקות Firebase נדרשים Java 21 ומעלה ו־Firebase CLI בגרסה 15.10.0:

```sh
npm install --global firebase-tools@15.10.0
npm run test:catalog
```

כדי להוסיף כיסוי לתיקון באג: מוסיפים בדיקה שמדגימה את ההתנהגות הרצויה ונכשלת לפני התיקון. קובצי `tests/*.test.ts` ו־`tests/e2e/*.spec.ts` נאספים אוטומטית; בדיקת אמולטור חדשה צריכה להיכלל גם ב־`scripts/test-catalog-emulators.mjs`.
